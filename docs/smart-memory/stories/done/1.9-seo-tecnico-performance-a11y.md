# Story 1.9: SEO técnico, performance e acessibilidade

As stories 1.4–1.8 entregam páginas; esta entrega o que faz o site ser **encontrado, compartilhável e utilizável por todos**. ### Estimativa estática pós-correção (rodada 3, 2026-09-09) — NÃO é medição de Lighthouse

**Método:** como a instrução da rodada 3 é explícita em não rodar `pnpm start`
de forma bloqueante, não tenho como rodar Lighthouse/axe-core nesta sessão.
Os números abaixo são sinais estáticos coletados do HTML pré-renderizado em
`.next/server/app/*.html` (saída de `pnpm build`) e do tamanho dos arquivos de
imagem em `public/images` — a mesma metodologia que o QA usou nas rodadas 1 e
2. **Isto é uma estimativa documentada, não uma pontuação de Lighthouse.**

| Rota | `<h3>` no HTML | `opacity:0` inline no HTML | `<img>` total | `alt=""` (decorativo, intencional) |
|---|---|---|---|---|
| `/` (index) | 10 | 0 | 7 | 7 |
| `/historia` | 16 | 0 | 5 | 5 |
| `/titulos` | 7 | 0 | 0 | 0 |
| `/estadio` | 0 | 0 | 7 | 7 |
| `/elenco` | 0 | 0 | 20 | 20 |

- **`opacity:0` = 0 em todas as rotas**, igual à rodada 2 — o fix de N2 (flash
  na hidratação) usa checagem síncrona no cliente (`useLayoutEffect` +
  `getBoundingClientRect`), nunca serializa estado oculto no HTML do
  servidor. Este é o mesmo sinal que sustentava a hipótese de LCP melhor na
  rodada 2 — continua válido.
- **100% dos `<img>` das 5 rotas têm `alt` deliberado** (vazio nos motivos
  gráficos genéricos após N3, preenchido onde há conteúdo real a descrever) —
  sinal a favor de zero violações de `image-alt` no axe-core, mas **não prova
  contraste, foco ou nomes acessíveis**, que o axe-core também audita.
- **Payload de imagem:** heros 30–33 KB, tiles de galeria/notícia 20–26 KB,
  timeline 9–13 KB, `public/images` inteiro = 448 KB (caiu de 560 KB da
  rodada 1 — remover o texto queimado de N4 reduziu levemente o peso do SVG
  rasterizado). Reforça a conclusão já registrada nas rodadas anteriores: o
  payload de imagem nunca foi o gargalo de LCP.
- **O que este método NÃO mede:** contraste real computado pelo browser
  (axe-core resolve `currentColor`/herança da forma que só um DOM renderizado
  faz), ordem de foco/tab, tempo de bloqueio de thread principal (TBT), LCP em
  ms. Nenhum desses sinais estáticos é substituto de Lighthouse — por isso
  AC8/AC9/AC11 continuam `[~]`, não `[x]`.

### Nota de performance — LCP simulado vs. real
O Lighthouse usa por padrão um modelo de throttling **simulado** (não observação literal) para os números de score/LCP, extrapolando a partir do trace real através de um modelo de rede+CPU (~slow 4G, CPU 4x). Contra `localhost` (sem CDN, sem latência real de rede), esse modelo pode inflar desproporcionalmente o LCP mesmo quando o recurso real é pequeno e rápido: o hero da Home, por exemplo, é servido pelo otimizador de imagem do Next em ~8KB e chega em ~200ms sob rede real (medido via `curl` direto, sem throttling). O breakdown do próprio Lighthouse (`lcp-breakdown-insight`) mostra picos de "resource load delay/duration" inconsistentes com o payload real. Isso é uma limitação conhecida de rodar Lighthouse contra `pnpm start` em `localhost` sem CDN — recomendação: revalidar CWV reais (RUM/CrUX ou Lighthouse contra o domínio de produção) após o deploy definitivo (fora do escopo desta story — depende do sites-devops).

### Otimizações aplicadas durante a auditoria
- `Reveal` ganhou `RevealGroup`/`RevealItem`: grids/listas (notícias, timeline, títulos, galeria, elenco) passaram de 1 observer/instância Motion por item para 1 observer por grupo com stagger orquestrado via `variants`. Reduziu o TBT da Home de **590ms para ~50-160ms** e elevou a Performance de 74 para 90-95 em todas as rotas.
- `MobileNav` (Sheet/Radix Dialog) convertido para `next/dynamic({ ssr: false })` no `SiteHeader` — o painel mobile só carrega após hidratação, com fallback do mesmo tamanho (sem CLS), reduzindo JS inicial de 192KB para 178KB (First Load JS da Home).

## Notas técnicas

- Usar a API de `metadata` do Next (`export const metadata` / `generateMetadata`), nunca `<Head>` manual.
- `metadataBase` precisa estar definido no layout raiz (Story 1.1) para OG e canonical resolverem absoluto. Se o domínio final ainda não existir, usar variável de ambiente com fallback e reportar ao lead.
- JSON-LD é dado estruturado sobre um clube real: preencher só com fatos vindos de `content/club` (rastreáveis ao research). Não inventar `sameAs`.
- Rodar Lighthouse contra `pnpm build && pnpm start`, **nunca** contra `pnpm dev` — dev inflaciona LCP e derruba o número.
- Se algum orçamento estourar, a causa mais provável é imagem (rota `/estadio`) ou fonte. Investigar nessa ordem antes de mexer em JS.
